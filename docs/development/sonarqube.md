# SonarQube development setup

FlintFire uses the SonarQube server at <https://sonar.casadega.dev>. The project key is
`reggieofarrell_flintfire_c1ad3ea7-e526-454b-a643-ba1d352f2d16` (GitHub-imported). Keep
`sonar-project.properties`, `.sonarlint/connectedMode.json`, and the VS Code
`sonarlint.connectedMode.project` binding in lockstep if that key ever changes.

## Layers

- **Local ESLint:** Casadega TypeScript Repo Tooling loads every active server rule implemented by
  its pinned `eslint-plugin-sonarjs` as a blocking error on production `src/` (tests, scripts, and
  the website remain excluded).
- **Agent post-edit hook:** a type-independent subset of that profile, generated by RuleSync.
  Findings fail the hook.
- **Pre-push precheck:** the real Scanner over files changed vs `origin/main`. Exit 2 (Scanner,
  credentials, or server unavailable) is a loud skip; findings and analysis failures still block.
- **CI:** the Tests workflow uploads both Jest LCOV reports, then calls the public
  [`Casadega-Development/action-workflows`](https://github.com/Casadega-Development/action-workflows)
  reusable scan. The server gate is **new-code-only** because this is a mature library, not a
  greenfield starter. Combined LCOV in Sonar is informational; path-specific gates in
  `scripts/check-coverage-gates.mjs` remain the coverage authority.

Neither the local plugin nor SonarQube for IDE replaces the server's complete analysis.

## CI setup

Create the project on the SonarQube server and configure these GitHub Actions values at the
**repository** level (avoid inheriting a different organization default):

| Name                      | Kind   | Value                                                                    |
| ------------------------- | ------ | ------------------------------------------------------------------------ |
| `SONAR_TOKEN`             | Secret | **Project analysis token** for this project key (not a user/login token) |
| `CASADEGA_PACKAGES_TOKEN` | Secret | Read-only GitHub token with access to the private shared tooling package |

Attach a quality gate whose conditions are on **new code**, not “any open issue.”

CI must use a **project analysis token** stored as the `SONAR_TOKEN` Actions secret. A SonarQube
**user** token (what `sonar auth login` puts in the macOS keychain for local `sonar:precheck`) is a
different kind: it authenticates a person, not the `flintfire` project. Either kind can analyze if
it has Execute Analysis, but the GitHub secret should be the project token so it is scoped to this
project and can be rotated without affecting developer logins.

The Tests workflow:

- runs on pull requests to `main` and on pushes to `main` (the latter re-baselines new code).
  `cancel-in-progress` applies only to pull requests so a `main` upload is not cancelled;
- intentionally does not support untrusted fork CI because dependency installation requires the
  private Casadega package token;
- calls a reviewed, immutable commit of
  `Casadega-Development/action-workflows/.github/workflows/sonar-scan.yml` and maps `SONAR_TOKEN`
  explicitly (`secrets: inherit` does not cross from this personal repository into the Casadega org;
  an inherited token arrives empty and the scanner returns HTTP 401);
- restores `coverage/unit` and `coverage/integration` from the Tests matrix artifacts;
- supplies explicit PR or branch parameters for the Community branch plugin;
- maps `CASADEGA_PACKAGES_TOKEN` to the reusable workflow's conventional `NODE_AUTH_TOKEN` secret;
- enforces `issue-gate-scope: new-code` plus the official quality-gate action.

SonarQube's configured GitHub integration owns pull-request decoration. The reusable workflow does
not post a second `github-actions` comment and therefore does not receive `pull-requests: write`.

Cloudflare in front of `https://sonar.casadega.dev` must skip Bot Fight / Managed Challenge for
scanner paths (`/batch*`, especially `/batch/project.protobuf`, and `/api/ce/submit`). A challenge
HTML 403 is reported by the scanner as “not authorized to analyze this project.”

The full CI scan is authoritative. External fork CI is intentionally outside the supported
maintenance model because this repository consumes private shared development tooling.

## Manual re-scan

The `SonarQube Re-scan` workflow can analyze an already tested commit without rerunning the entire
quality pipeline. Open a completed `Tests` run, copy the numeric run ID from its Actions URL, and
supply it to the manual workflow. It is a thin caller of the same reviewed commit of
`Casadega-Development/action-workflows/.github/workflows/sonar-scan-after-tests.yml`, which restores
that run's coverage artifacts and derives the original PR or branch context before scanning.

## Local command-line setup

Install both SonarQube Scanner and SonarQube CLI. Scanner performs the temporary changed-file
analysis; the CLI continues to power the pre-commit and pre-push secret-scan hooks. On macOS,
Scanner is available through Homebrew:

```bash
brew install sonar-scanner
```

Install SonarQube CLI with SonarSource's installer, then authenticate once to the configured server.
Always include `--server`; omitting it selects SonarQube Cloud EU rather than this repository's
server:

```bash
curl -o- https://raw.githubusercontent.com/SonarSource/sonarqube-cli/refs/heads/master/user-scripts/install.sh | bash
sonar auth login --server https://sonar.casadega.dev
```

Shared repository tooling does not follow SonarQube CLI's single active server. On macOS, store a
user token under the endpoint-scoped service selected for the committed host:

```bash
security add-generic-password -U -s sonarqube-cli-sonar.casadega.dev -a sonar.casadega.dev -w
```

The value-less `-w` prompts without echo, and `-U` makes the command safe to repeat. Do not append
the token to that command. The endpoint-scoped item is sufficient for `sonar:precheck`,
`sonar:rules`, and `sonar findings` even when `sonar auth status` points at another server. The
shared commands query the committed endpoint directly and never issue hostless CLI API requests.

On non-macOS platforms, the local precheck has no verified credential-store adapter and uses
`SONAR_TOKEN` only. Supply a SonarQube **user token** without putting it in shell history, then
remove it when the session ends:

```bash
read -rs SONAR_TOKEN
export SONAR_TOKEN
printf '\n'
# Run the required command, then remove the session credential.
unset SONAR_TOKEN
```

Do not reuse the CI project-analysis token locally: the precheck also calls user-facing issues and
branch APIs. Never print a keychain token with `security find-generic-password ... -w`; the precheck
captures that command's output internally without writing the secret to the terminal.

For all repository-local Sonar tooling, the committed `sonar.host.url` is the only server authority.
An inherited `SONAR_HOST_URL` is never used as an override or fallback; a conflicting non-blank
value is reported and ignored. Missing committed host configuration blocks instead of becoming a
skippable precheck prerequisite. Authentication resolves from the endpoint-scoped keychain item,
then `SONAR_TOKEN` or `SONAR_USER_TOKEN` as portable fallbacks.

```bash
npm run sonar:rules
npm run sonar:check
npm run sonar:precheck
npm run sonar:precheck -- --all
npm run sonar:precheck -- --base another-base-branch
```

`sonar:rules` intersects active server rule IDs with rules implemented by the shared tooling's
pinned SonarJS plugin. Before the project is provisioned it uses the server-default profiles;
afterward it automatically uses profiles associated with the project. `--bootstrap` remains an
initial-project fallback, not an authentication workaround. `sonar:check` deterministically
validates the committed host, project identity, generated-profile provenance, and local rule IDs
without credentials or network access.

The normal precheck reports issues introduced compared with `origin/main`. `--all` includes
pre-existing issues in every changed file. The script uses a short-lived server branch and removes
it after reading the findings.

Never put Sonar tokens in source files, committed environment files, command arguments, shell
history, or logs.

## Git hook behavior

Husky installs three complementary hooks during `npm install`:

- `pre-commit` runs the SonarQube CLI secret scan, then lint-staged.
- `commit-msg` enforces Conventional Commits through commitlint.
- `pre-push` runs the outgoing secret scan, the changed-file SonarQube analysis, then the existing
  unit coverage gate (`rules:check`, types, doc links, zod-idiom scan, unit coverage).

Secret scan failures always block. The changed-file server analysis exits with status 2 when
Scanner, credentials, the base branch, or the server is unavailable; pre-push reports the skip and
continues to the other checks. Findings, rejected credentials, and scanner failures still block.

## Coding-agent feedback

RuleSync generates a post-edit hook for Codex, Cursor, and Claude. The hook extracts edited
repository paths from each tool's event payload and runs a bounded, type-independent subset of the
generated SonarJS configuration, only on production `src/` files that `npm run lint` also analyzes.
Findings are printed near the edit and the hook exits unsuccessfully.

Edit `.rulesync/hooks.jsonc` or `scripts/agent-hooks/scan-edited-file.mjs`, then run
`npm run rules:sync`; do not edit generated tool hook files (`.cursor/hooks.json`,
`.claude/settings.json`, `.codex/hooks.json`) directly.
